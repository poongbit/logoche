# 로고체 엔진

웹(`web/`)의 API 라우트가 부르는 Python 서버다. 로고 측정, 기준 글자표, 글자표 나누기·자리 맞추기, 그린 2,350자의 TTF 빌드, 구조 검사를 맡는다. AI 호출(GPT Image·Claude)은 모두 웹 서버가 한다. 키와 모델 설정은 환경 변수에서 읽고, 없으면 `web/.env.local`에서 읽는다(키를 한 곳에만 둔다).

10/30 결정: MX-Font를 뺐다. 이미지 API가 기준 글자 30자에 이어 나머지 글자까지 KS X 1001 한글 2,350자를 그리고, 엔진은 그 그림으로 바로 외곽선을 딴다(`drawn.py`). MX-Font 코드는 저장소에서 뺐다. 만든 서체는 10/29 결정대로 SIL OFL 1.1로 낸다(상업 사용 가능, 서체 파일만 따로 팔지 않음. MX-Font를 빼서 OFL로 묶을 이유는 사라졌고, 바꿀지는 사용자 결정). 출처는 `LICENSE-NOTES.md`.

## 실행

```bash
cd engine
uv sync                                                        # 처음 한 번
uv run uvicorn logoche_engine.main:app --port 8000 --reload    # http://127.0.0.1:8000/health
```

웹은 `FONT_ENGINE_URL`(기본 `http://127.0.0.1:8000`)로 이 서버를 부른다.

기준 서체 파일(`assets/fonts/SourceHanSansKR-{Regular,Bold}.otf`)이 없으면 다시 받는다.

```bash
for w in Regular Bold; do curl -sSL -o assets/fonts/SourceHanSansKR-$w.otf \
  "https://raw.githubusercontent.com/adobe-fonts/source-han-sans/1.001R/SubsetOTF/KR/SourceHanSansKR-$w.otf"; done
```

|---|---|

| `POST /sheets/glyphs` | `chars`(기준 글자)의 기준 글자표 PNG와 격자(열·행·가로세로비). 30자면 6열×5행, 4:3 |
| `POST /sheets/glyphs/split` | 이미지 API가 그린 글자표를 칸별 음절 그림으로 자르고, 검사용 번호 붙은 모음 그림을 만든다 |
| `POST /sheets/glyphs/place` | 나머지 글자 한 장을 칸별로 잘라 바로 폰트 틀에 자리를 맞춘다(`refs`의 획 두께에 맞춤). 칸마다 자리 맞춘 흑백 PNG(1em = 500px, 650px 정사각형)와 검사용 모음 그림 |
| `GET /sheets/glyph?char=` | 음절 하나의 기준 그림(한 자씩 다시 그릴 때, 직접 그릴 때 밑그림) |
| `POST /sheets/word` | 가게 이름 견본의 기준 그림(2·3자는 한 줄, 4자는 2×2) |
| `POST /glyphs/normalize` | 한 자씩 다시 그린 그림을 글자표 칸과 같은 형식으로 자른다 |
| `POST /preview` | 그린 글자(`refs` 기준 글자, `glyphs` 글에 든 나머지 글자)와 조절값으로 글 몇 자(최대 80자)만 빌드와 같은 방법으로 만들어 글자별 SVG 패스(y 아래쪽, 위 끝 = ascender)로 돌려준다. 그리지 않은 글자는 `path: null` |

| `POST /glyphs/parts` | 글자를 초성·중성·종성 영역으로 나눠 영역별 외곽선(SVG 패스)과 경계선을 돌려준다(부분 끌어서 바꾸기, 11/11). 자동으로 찾은 경계는 `tweak.cuts`로 옮긴다. 글자별 조정(`tweak`)의 `parts`는 빌드·미리보기·글자 바꿔 끼우기에서 영역별로 걸리고, 표의 `cho:ㅂ` 같은 열쇠는 같은 초성·중성·종성을 가진 모든 글자에 얹힌다(`drawn.with_groups`) |
| `POST /glyphs/edit-source` | 글자 고치기 편집 화면 그림(512px, 폰트 틀과 같은 자리): 지금 글자·그린 그대로(못 그린 글자는 빈 그림)·글자 틀 자리 |
| `POST /builds/{id}/glyph` | 만든 TTF에서 글자 하나만 다시 따서 바꿔 끼운다(고친 그림, 없으면 그린 그대로). 서체에 없던 글자면 새로 넣고 글자 세트 검사를 다시 한다. 비었거나 깨진 외곽선은 400 |
| `GET /builds/{id}` | 진행 단계(`stage`: queue → trace 외곽선 → save TTF → check 검사), 단계별 개수·걸린 시간(`stages`), 지난 시간(`elapsed`)·남은 시간 어림(`remaining`), 검사 7항목, 유사도 |
| `GET /builds/{id}/font.{ttf,otf,woff,woff2}` | 만든 TTF, 또는 TTF에서 만든 OTF(CFF, 2차 곡선을 3차로 그대로 옮김)·WOFF·WOFF2(brotli). 빌드가 끝나거나 글자를 고치면 뒤에서 미리 만든다(처음 OTF 약 7초, WOFF2 약 5초) |
| `POST /builds/{id}/bundle` | 모두 받기 zip: TTF·OTF·`웹폰트/`(WOFF2·WOFF·CSS 예시)·OFL 원문과 받은 글 파일 |
| `POST /builds/{id}/ocr-sheet` | OCR용 그림(번호 붙은 글자 격자). 서체에 있는 글자만 놓고 놓은 글자(`chars`)를 돌려준다. 판독은 웹이 Claude로 한다 |
| `POST /builds/{id}/issue` | 발급 대장에 올린다(기록용, 다른 서체의 검사에는 쓰지 않음) |

## 어떻게 만드나 (10/30, 그린 글자로 바로)

1. **기준 글자** (`sheets.py`, 웹 `lib/server/glyphs.ts`): 기준 서체로 기준 글자 30자를 칸마다 하나씩 놓은 기준 글자표를 이미지 API에 철자·칸 참고로 준다. 돌아온 그림을 글자 사이 빈 띠(줄·열의 잉크 합이 가장 적은 곳, 10/30)에서 자르고 빈 칸·칸 넘침·격자선 흔적을 걸러 낸다. 검사·다시 그리기는 웹이 한다.
2. **나머지 글자** (웹 `lib/server/rest.ts`, `POST /sheets/glyphs/place`): 웹이 기준 글자 글자표를 스타일 참고로 붙여 나머지 글자를 30자씩 그린다. 엔진은 글자표를 칸별로 잘라 바로 폰트 틀에 자리를 맞춘다.
3. **자리 맞추기** (`drawn.py`): 한 장에서 온 글자는 한 배율로 키운다(글자마다 기준 서체 같은 글자와 잉크 넓이가 같아지는 배율의 가운데 값, 그와 1.5배 넘게 다른 글자만 제 배율). 그래서 글자 사이 크기 차이는 그린 대로 남는다. 자리는 기준 서체 같은 글자의 잉크 상자 가운데, 나머지 글자 장은 획 두께를 기준 글자에 맞춘다(10/30 시험에서 장마다 0.89~0.93배로 조금 가늘었다). 틀은 폰트 단위 x −150~1150, y −270~1030 정사각형이고, 1em = 500px로 놓는다. 편집 화면(512px)도 같은 틀이다.
4. **외곽선** (`drawn.py`, `contour.vtrace`): 굵기 축은 그린 굵기(`drawnWeight`)와의 차이만큼 윤곽을 옮긴다(기준 서체 Regular·Bold를 같은 배율로 그려 잰 굵기 1당 두께, `raster.keep_shape`로 속공간·획 수 지킴, 둥글기 0.35 아래면 정사각형 커널). 글자 둘레만 잘라 vtracer로 따고 폰트 단위로 바꾼 뒤 너비·기울기·자간(`contour.style_transform`)을 건다. 10/30 시험: TTF와 그린 그림의 겹침 0.97~0.99, 획 끝 물결 같은 장식이 그대로 남는다.
5. **빌드** (`build.py`): fontTools로 TrueType을 만든다. 그린 글자(+ 고친 글자) + 공백, fsType 0, 이름 정보에 한국어 이름·OFL 고지(nameID 13·14)·AI 생성 표시와 권리 요약(설명 칸)을 넣는다. 이미지 모델이 끝내 그리지 못한 글자는 넣지 않고, 화면 4 글자 고치기로 그려 넣으면 바로 바꿔 끼운다.
6. **검사** (`checks.py`): 글자 세트(빠진 글자를 알림), 깨진 글자(윤곽 자기교차), 문서 포함 허용, 이름·라이선스, 기기별 표시(구조 검사), 크기 기준(12px 뭉침·96px 속공간), 유사도.

엔진 빌드(외곽선·TTF·검사)는 11/3 실측에서 2,288자에 외곽선 14.9초 + 저장 0.8초 + 검사 1.8초였다(Claude 판독 8.4초는 웹). 오래 걸리는 것은 웹의 나머지 글자 그리기다(표준 실측 약 4.8분, 장당 중앙값 13.5초, 동시 8장). 2026-11-03 전체 실측은 `docs/full-run-20261103.md`.

## 임시 값

| 값 | 지금 | 위치 |
|---|---|---|
| 유사도 기준값 | 0.85 (뼈대 겹침 점수) | `checks.py` `SIMILARITY_THRESHOLD` |
| 크기 기준 | 12px에서 글자 상자의 72% 넘게 칠해지거나, 96px에서 기준 서체보다 속공간이 적은 글자가 5% 이하 | `checks.py` |
| 굵기·너비 측정 보정 | 기준 서체로 쓴 "달콤한집"을 같은 방법으로 재서 Regular 400 · Bold 700에 맞춤 | `measure.py` |

유사도는 글자 크기를 맞춘 뒤 획 가운데 선(뼈대)이 같은 자리를 지나는 비율(F1)로 잰다. 굵기 차이는 보지 않는다. 10/27 보정값: 같은 가족 다른 무게 0.95~0.96, Source Han Sans와 애플 산돌고딕 Neo 0.91~0.95, 애플고딕과는 0.71~0.77, 명조와는 0.53~0.59. 기준 서체의 자모를 그대로 넣어 만든 시험 서체는 0.73~0.76이 나왔다.

10/28 점검: 뼈대를 잡기 전에 중간값 거르기(5px)를 한다. 안 거르면 붓 질감(가장자리 요철·마른 붓 틈)마다 뼈대 가지가 생겨, Source Han Sans에 질감만 입힌 사본이 0.79~0.82로 기준 아래(통과)가 됐다. 거른 뒤 0.92~0.96으로 잡히고, 다른 서체 점수는 ±0.02 안에서 그대로다(Source Han Sans 기준 Pretendard 0.99, 넥슨 Lv1 고딕 0.71~0.79, G마켓 산스 0.56, 전남교육유나체 0.31). 다만 전남교육또박체 ExtraBold처럼 따로 만든 고딕도 0.86이 나와, 고딕끼리는 0.85가 빡빡할 수 있다(기준값은 정할 것 7).

10/28 기준값 다시 잼(비교 폰트 69개, 52가족):

| 무엇끼리 | 점수 |
|---|---|
| 서로 다른 가족 2,329쌍 | 중앙값 0.40 · 95% 0.84 · 99% 0.92 |
| 같은 뿌리(Pretendard·SUIT ≈ Source Han Sans, 나눔고딕 ≈ 나눔고딕코딩) | 0.98~0.99 |

| 질감만 입힌 사본 → 원본(10종, 질감 세기 3단계) | 0.76~0.98 (평범한 고딕 0.91 이상, 아주 굵은 디스플레이체·붓글씨체는 0.74~0.85) |

뼈대만 보는 점수라 관습적인 본문용 고딕·명조끼리는 따로 만들어도 높게 나오고, 아주 굵은 글씨에 질감을 세게 입힌 사본은 낮게 나온다. 두 분포가 겹치는 구간이 있어 한 값으로 완벽히 가를 수 없다. 사본을 놓치는 쪽이 더 위험하고 우리 빌드는 10/28까지 0.77 이하였으나 11/3 고양이 로고 전체 실측에서 0.83(Pretendard Bold)이 나와 기준 0.85와 가깝다. 아직 통과하지만 여유가 작아 기준값은 로고를 더 늘려 재검토한다. 이 검사는 선별 검사이고 권리 보증이 아니다(웹 `RIGHTS.screening`).

## 유사도 비교 대상

- 무료 폰트: 기준 서체 2종은 늘 들어간다. 더 넣으려면 `compare/free/`에 `.otf`·`.ttf`를 둔다. 10/28 기준 69개(52가족):
  - Google Fonts의 한글 가족 38개, 47개 파일: `uv run python scripts/fetch_compare_fonts.py`로 다시 받는다(목록·해시 `compare/free/google-fonts.json`).
  - 사용자 맥에 깔려 있던 무료 폰트 10가족 20개 파일(Pretendard·SUIT·G마켓 산스·넥슨 Lv1 고딕·학교안심 알림장·강원교육·전남교육·심경하체): 목록·해시·약관 문구 `compare/free/local-fonts.json`.
  - 엔진을 켤 때 뼈대를 미리 만든다(`checks.warm_comparison`, 약 2.4초). 빌드마다 비교는 0.02초 안팎이다.
- 상용 폰트: `compare/commercial/`에 둔다. 지금은 비어 있다(design.md 정할 것 5). 비교에 쓸 권한이 있는 파일만 넣는다. 이 폴더는 깃에 올리지 않는다. 비어 있으면 검사 결과에 "상용 폰트는 비교 안 함"이라고 적는다.
- 견본 이미지(11/5): 폰트 파일이 없는 폰트는 글자표 캡처·사진으로 비교할 수 있다. `uv run python scripts/add_specimen.py 글자표.png --name "이름" --chars "가나다…" [--grid 2x5] --source "약관 확인 메모"`로 `compare/specimen/<이름>/`에 등록한다(글자를 나눈 `preview.png`를 같이 만든다). 글자 수가 맞지 않으면 등록하지 않고, 이미지 파일은 깃에 올리지 않는다(`meta.json`만 올린다). 글자는 긴 변 24px 이상이어야 하고 비교에 쓰는 샘플 글자가 8자 이상 겹쳐야 한다. 합성 글자표 시험(`tests/test_specimen.py`): 깨끗하면 0.99, 글자 약 44px·JPEG 50이면 0.98, 약 33px·JPEG 35면 0.92로 파일 기준보다 낮아진다. 실제 사이트 캡처(11/5, agfont.com NU Siya 글자표를 화면 캡처, 칸선·위에 뜬 팝업이 있던 이미지): 글자 약 21px(1배율)는 거절, 약 42px(2배율)는 자동 나누기와 grid 지정이 같은 지문(둘 사이 1.00)을 냈고, 무료 폰트 중 가장 가까운 것은 0.44(Yeon Sung)로 조건 없이 낮았다. 칸선은 `specimen._without_rules`가 지우고 글자·바탕 방향은 더 많은 쪽을 바탕으로 읽는다. 눈누(noonnu.cc) 정답 대조(11/5): G마켓 산스 페이지의 "미리 써보기" 칸에 샘플 글자 30자를 넣어 캡처(글자 긴 변 약 138px)하고 로컬 폰트 파일과 비교했다. Medium 캡처 ↔ Medium 파일 0.989, Bold 캡처 ↔ Bold 파일 0.976(둘 다 지문 30자), 반해상도+JPEG 50으로 낮춰도 0.986·0.972. 다른 굵기끼리는 0.89·0.85(굵기는 보지 않는 점수), 다른 가족 최고는 0.86(학교안심 알림장). 같은 서체와 다른 서체의 점수 차는 크지만 기준 0.85 바로 위까지 다른 가족이 올라올 수 있다. 눈누는 무료 폰트 모음이라 이 대조는 파이프라인 검증용이고, 유료 폰트 공백은 메우지 못한다. 눈누마켓 유료 폰트(SF겨울명조, 11/5): 미리 써보기 칸은 읽기 전용이고 정해진 문장 한 줄(13자, 웹폰트도 그 글자만 담은 부분집합)만 보여 준다. 그래서 견본 비교는 샘플 글자 109자가 아니라 견본에 든 한글 글자로 맞춰 그린다(`checks.shape_set_for_chars`, 견본 지문이 8자 이상이어야 비교). 굵기 100·300·500은 칸이 올바르게 나뉘었고(눈으로 확인) 무료 폰트 중 가장 가까운 것은 0.57~0.64라 닮은 폰트가 없었으며, 같은 가족 굵기끼리는 0.84·0.91로 높게 나왔다. 굵기 700·900은 글자가 서로 붙어 있어 자동 나누기를 거절한다. 이 과정에서 "글자 수만 맞으면 통과"가 틀린 칸을 통과시키는 것을 발견해(합쳐진 두 글자와 쪼개진 한 글자가 수를 상쇄) 칸 너비 검증(`specimen.plausible`)을 넣었다. 한 줄 견본은 글자가 붙으면 못 나누므로 칸이 갈라진 글자표(grid)를 우선한다. 기준값(`SPECIMEN_THRESHOLD`)은 아직 파일 기준과 같은 0.85이고 보정 전이다. 폴더가 비어 있으면 검사 결과는 전과 같다. 이미지 수집은 사이트 약관이 허용하는 곳만, 손으로 고른 소수만 쓴다. 눈누(noonnu.cc) 약관(이용약관 제7조·제13조, 눈누마켓 약관 제9조, 11/5 확인)은 서비스 내용을 자동·비자동 스크래핑으로 복사하거나 사전 동의 없이 가공·복제·파생하는 것을 금지하므로, 눈누 견본을 비교 집합으로 모으려면 눈누와 제작사의 사전 동의가 먼저다. 위 시험 캡처는 파이프라인 검증용 소량이었고 저장하지 않았다.
- 발급 대장과는 비교하지 않는다(10/30 결정: 서체마다 따로 만든다). MX-Font로 만들던 때(10/30 전) 서체끼리 뼈대가 거의 같아서(러너스하이·와사비 0.88), 앞서 받아 간 서체가 다른 가게의 새 서체를 막았다. 웹에서 폰트를 받으면(`?download=1`, 모두 받기) `data/issued/`에 올라가지만 무엇을 내보냈는지 남기는 기록일 뿐이다.

## 데이터

`data/`(깃 제외): `cache/corpus/` 글자 순서용 말뭉치, `builds/<id>/font.ttf` 만든 서체, `builds/<id>/provenance.json` 빌드 출처(11/5부터: 방식 이름·시각·조절값·글자 수와 웹이 넘긴 프로젝트 번호·서체 방향. 가게 이름·소유자·로고 이미지는 넣지 않는다. 서체끼리의 유사도 분석에서 같은 로고의 재빌드와 서로 다른 로고를 가르는 데 쓴다, `docs/similarity-analysis-20261105.md`), `issued/` 발급 대장. 빌드 진행 상태는 메모리에 있어 서버를 다시 켜면 사라지고, TTF 파일은 남는다.
